# An Obsidian vault as the shared memory of Claude Code

Claude Code's auto-memory is keyed on the folder you start a session in. That is good for facts about one checkout. It is not good for knowledge that belongs to a project spanning several repos, or to all your work at once: why you chose X over Y, what went wrong last time, what is blocked where.

We keep that second kind of knowledge in a plain Obsidian vault: Markdown files in a Git repo. Claude reads from it at session start and writes to it through a few commands. Scripts keep the overview notes up to date. We open the same files in Obsidian to read, link and think.

This playbook describes the pattern. The vault scripts themselves are not yet published; we plan to. The two commands and the leak gate mentioned below are in this repo.

## The idea behind it

Andrej Karpathy described this as an [LLM wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f): instead of retrieving from raw sources on every question, let the model build and maintain a persistent wiki that grows over time. The human curates and asks; the model does the bookkeeping (cross-references, summaries, checks).

He uses three layers, and so do we:

- **Raw sources**, never edited by the agents: Claude's auto-memory, git history, documents you drop in, your own prompts.
- **The wiki**: the vault itself.
- **The schema**: one document that tells every agent and session where things go and which frontmatter each note type needs. Only the human edits it. An agent that could rewrite its own rules would be going in circles.

Our main adaptation: we work across many projects, not one subject, so we added the project note, a cap on how many pages one ingest may touch (five), and several lint scripts instead of one.

## Layout: PARA plus two

```text
~/vault/
  00-Inbox/        quick capture, sorted later
  01-Projects/     one note per active project
  02-Areas/        ongoing responsibilities without an end date
  03-Resources/    decisions/, learnings/, patterns/, reference
  04-Archive/      finished or dormant work (agents only move files here)
  05-Daily/        one note per day
  _meta/           schema, overview notes (MOCs), generated indexes
  _templates/      one template per note type
  Memory/          read-only mirror of Claude's auto-memory
```

PARA (Projects, Areas, Resources, Archive) is Tiago Forte's method. Inbox and Daily are the two additions. Every note type has exactly one home folder; a note in the wrong folder is a lint error.

## One project note per repo

Each project gets a note in `01-Projects/` with frontmatter that ties it to its code:

```yaml
---
type: project
status: active
priority: medium
tech: [nextjs, postgres]
repo: ~/code/acme-shop
created: 2026-03-02T09:00:00Z
tags: [project/active]
---
```

The `repo:` field is what makes the vault project-aware. A SessionStart hook looks at the current working directory, finds the project note whose `repo:` matches, and injects it into the session together with today's daily note and the open blockers. It has a budget of 200 ms and is warn-only: if the vault is missing, the session still starts.

Use `aliases:` for old names of a project, so a decision filed under the old name still finds its way home.

## Decisions and learnings, dated and typed

Two kinds of note carry most of the value:

- **Decisions** (ADRs, after Michael Nygard): context, decision, alternatives considered, consequences, status (`proposed`, `accepted`, `superseded`, `deprecated`).
- **Learnings**: what happened, what we learned, root cause, how to apply. Typed as `gotcha`, `success`, `failure` or `anti-pattern`.

Both live in `03-Resources/`, named by date and title (`2026-03-14-idempotency-key-is-the-order-id.md`), with a `project:` field and a link back to the project note. We write them with `/decision <project> "<title>"` and `/learning <project> "<title>"`. Both commands are in [`commands/`](../commands/). The templates exist as a manual fallback.

When the same lesson shows up in three or more projects, it becomes a candidate pattern in `03-Resources/patterns/`. A weekly script suggests these; a human accepts them.

## Overview notes that rebuild themselves

Some notes are pure views: what we worked on this week (from git activity per `repo:`), what is blocked across projects, how notes link to each other, broken links and orphans. Scheduled scripts rebuild them from scratch on every run. They are idempotent and write atomically.

Each one starts with a banner:

```markdown
_Generated by focus-monitor on 2026-03-14T06:00:00Z. Do not edit by hand; overwritten on every run._
```

That banner matters. Without it, someone adds a useful line, the next run wipes it, and trust in the whole system drops. Put your own thoughts in a normal note and link to the view.

## A one-way mirror of Claude's memory

A small script copies `~/.claude/projects/*/memory/` into `Memory/` in the vault, one folder per project. It runs from a hook after memory writes, with a scheduled fallback. It is one-way: nothing in the vault ever writes back, and agents treat `Memory/` as read-only.

Why bother: it makes the auto-memory of all projects searchable and linkable in one place, without making the vault a second source of truth for it. The [memory hygiene playbook](memory-hygiene.md) covers what belongs in the auto-memory itself.

## Sync via Git, not iCloud

The vault is a private Git repository. The Obsidian Git plugin commits and pushes on a timer. We deliberately keep the vault out of iCloud: scripts and Obsidian writing the same files while a cloud sync runs is a recipe for race conditions and conflict copies. Git gives us history, diffs, and a clear answer when two writers disagree.

## The "stand" block: the model writes, the script guards

Each project note has a block with the current state: where it stands, what holds (with a link to the decision behind each line), lessons that still apply, and what is open.

Writing that summary takes judgement, so the model writes it. Everything that should not depend on judgement is done by a script:

1. It hands the model the sources: decisions, learnings and open actions for the project, with new ones since the last update marked.
2. It checks what comes back: the four fixed headings, a line limit, a source link on every line under "What holds" and "Lessons", and no superseded or deprecated decision cited as if it still holds.
3. It writes the block between two markers, atomically (temp file, then rename), and touches nothing outside the markers.
4. It stores a checksum of the block in the frontmatter. If the block on disk no longer matches, someone typed in it; the script moves that text to a "manual notes" section instead of throwing it away.
5. A daily check lists every project whose sources are newer than its block.

```markdown
<!-- stand:begin (managed; do not edit by hand) -->
## Stand
### Where it stands
### What holds
### Lessons that still apply
### Open
<!-- stand:end -->
```

The model writes, the script guards. The same split works for most places where an LLM writes into a file that other tools depend on.

## Dossiers: share part of a private vault

Sometimes another person should see part of what you know, for example a client who wants the decisions on their project. Giving them the vault is out. What we do instead:

- **Opt-in per note.** Only notes with `share: [audience]` in their frontmatter go into that audience's dossier. Nothing is shared by default.
- **A derived folder**, built from a small description file per audience. The build never pushes to a remote on its own, and refuses to overwrite a target that was edited by hand.
- **A gate that refuses the whole export on one hit.** Before anything is written, every page is checked for amounts and pricing words, IP addresses and email addresses, key shapes, internal links and home paths, names outside an allow list, and anything from private folders (daily notes, the people folder, the memory mirror, our personal assistant's area). One hit, nothing is written.

Our first attempt taught us the rest. Notes proposed for sharing by title looked fine and the gate was green, yet a separate check over the built folder still found addresses, figures and names of config files. A title does not tell you what is in the text, and a green gate only proves its own rules found nothing. So: read every note on content before marking it shareable, expect most to need their own shareable text, run an independent check after each build, and turn every find into a new gate rule with a planted leak in the test set.

The [leak gate](../scripts/leak-gate/) in this repo follows the same idea for a folder you are about to publish.

## Getting started

You do not need all of this on day one. A useful order:

1. A vault in Git with the PARA folders and a short schema note.
2. Project notes with `repo:`, and a SessionStart hook that loads the matching one.
3. `/decision` and `/learning`.
4. One generated view (for example, this week's activity) with the banner.
5. The memory mirror, the stand block, dossiers, when you feel the need.
